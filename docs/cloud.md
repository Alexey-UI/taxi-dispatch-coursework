# Будущее развёртывание в Yandex Cloud и публичный домен

Это подготовленная инструкция. ВМ, платные ресурсы, DNS и сертификаты в ходе локальной разработки не создавались. Конкретный домен и параметры облачного аккаунта пока не заданы.

## Схема
Интернет → DNS A → публичный IPv4 ВМ → TCP 80/443 → Traefik → Nginx/web → API → PostgreSQL/Redis. На ВМ устанавливается K3s непосредственно, без вложенного k3d. Тот же Helm chart описывает приложение. Одна ВМ — учебный стенд с единой точкой отказа.

## 1. ВМ и сеть
Ориентир для стенда: Linux Ubuntu 24.04, 2 vCPU, 4 ГБ RAM, диск 30 ГБ; фактическую ёмкость нужно оценить по нагрузке. Terraform в `deploy/terraform/` — необязательная заготовка вместо ручного создания. До apply проверьте provider, регион, квоты, стоимость и полный план. Токен используйте через окружение YC_TOKEN, не через исходники. В репозитории нет tfstate и рабочих tfvars. Заготовка не выполнялась против облака.

Публично открываются 80/443. SSH доступен только с доверенного IPv4 /32. PostgreSQL:5432, Redis:6379 и Kubernetes API:6443 не публикуются в интернет. Администрирование API возможно через SSH tunnel. Для постоянного домена заранее закрепите публичный IP: динамический NAT-адрес может измениться при жизненном цикле ВМ.

Внутренняя сеть ВМ в заготовке 10.80.0.0/24; она не пересекается с обычной Pod-сетью K3s 10.42.0.0/16. При изменении сетей проверяйте маршруты и доверенные прокси Nginx.

## 2. K3s
Выберите поддерживаемый выпуск K3s и прочитайте установочный скрипт перед выполнением. Официальная точка входа: https://docs.k3s.io/quick-start. Поставьте один server; сохраните kubeconfig с правами 0600. Установите Helm. Не копируйте административный kubeconfig в репозиторий или публичный CI artifact.

Установите release приложения по SHA образов из успешного GitHub Actions. У пакетов GHCR отдельно проверьте видимость: публичный GitHub-репозиторий не гарантирует публичный container package. Можно сделать пакеты public либо настроить imagePullSecret с read:packages; значение токена не хранить в chart.

## 3. Секреты
На ВМ выполните `node scripts/setup.mjs` или подготовьте аналогичный `.env` с новыми случайными ключами. Использовать локальные демонстрационные ключи в интернете не следует. Передайте секреты напрямую:
```sh
kubectl create namespace taxi
node scripts/kube-secret.mjs | kubectl apply -f -
```
Не запускайте генератор секрета без pipe: stdout содержит значения. Не помещайте секреты в Helm --set, shell history, скриншоты и отчёт. Все реплики должны получать одинаковый SESSION_KEY. Его смена завершает действующие сессии.

## 4. DNS и HTTPS
Создайте A-запись поддомена, например taxi.example.org, на закреплённый IPv4. Не создавайте AAAA, если IPv6 на сервере не настроен. Проверьте DNS с внешней сети и доступность TCP 80.

Установите cert-manager по официальной инструкции: https://cert-manager.io/docs/installation/helm/. Его CRD и контроллеры должны быть готовы до использования issuer. В `deploy/cloud/issuer.yaml` замените email. Для первичной отладки используйте staging endpoint ACME и отдельное имя issuer; затем переключитесь на production. HTTP-01 требует внешней доступности challenge по домену. Описание механизма: https://cert-manager.io/docs/configuration/acme/http01/.

NetworkPolicy приложения разрешает временные solver-поды cert-manager из Traefik namespace. Установка cert-manager в отдельном namespace не должна наследовать deny-политику приложения. Проверьте `kubectl describe certificate`, `kubectl get challenges,orders -n taxi`.

В копии values-cloud.yaml замените owner, SHA и домен:
```sh
helm upgrade --install taxi deploy/helm/taxi -n taxi -f deploy/helm/taxi/values-cloud.yaml --wait --timeout 180s
```
Файл содержит шаблонные значения и не должен запускаться без замены. Включены TLS и Secure cookie. После выдачи сертификата примените `deploy/cloud/traefik.yaml` для перенаправления HTTP на HTTPS. Проверьте редирект и сертификат из внешней сети. Добавление HSTS имеет смысл после устойчивого подтверждения HTTPS; includeSubDomains не включайте для домена с неизвестными соседними сервисами.

## 5. Доставка новой версии
GitHub Actions автоматически проверяет систему в временном кластере и публикует образы по SHA. Доставка на реальную ВМ пока выполняется оператором: выбрать успешный SHA → сделать backup → изменить три image → helm upgrade --wait → проверить /api/state и создание заказа. `helm rollback` возвращает конфигурацию релиза, но не откатывает данные PostgreSQL. Для несовместимых миграций нужен отдельный план.

## Приёмка публичного стенда
С телефона через мобильную сеть открывается HTTPS-домен; сертификат доверен; HTTP перенаправляет на HTTPS; аноним видит карту и не меняет симуляцию; гость создаёт заказ; rate limit возвращает 429 при избытке запросов; БД/Redis/API управления не доступны через публичные порты. Проверяется восстановление из независимого дампа и доступность свободного места. Реальные технические логи доступны только оператору.
